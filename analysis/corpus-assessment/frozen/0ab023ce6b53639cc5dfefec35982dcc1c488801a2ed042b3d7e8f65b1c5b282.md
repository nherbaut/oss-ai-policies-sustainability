<div id="mw-content-text" class="mw-body-content">

<div class="mw-content-ltr mw-parser-output" lang="en" dir="ltr">

<a href="https://nura.eco/" class="external text" rel="nofollow">Nura</a> extends the <a href="https://en.wikipedia.org/wiki/Free_software" class="external text" rel="nofollow">free and open source</a> operating system <a href="https://alpinelinux.org/about/" class="external text" rel="nofollow">Alpine Linux</a> to run on smartphones and other mobile devices. Alpine is a security-oriented, light-weight Linux distribution based on <a href="https://musl.libc.org/" class="external text" rel="nofollow">musl libc</a> and <a href="https://busybox.net/" class="external text" rel="nofollow">BusyBox</a>.

Currently, Nura is for Linux enthusiasts. In the long term, Nura shall empower ordinary people to be in control of their phone (and not the other way around).

Until 27 September 2026, Nura was called postmarketOS.

## <span id="Status" class="mw-headline">Status</span>

Nura is for Linux enthusiasts. The more complete [device ports](/wiki/Devices "Devices") (mostly aarch64 devices in main and community categories) are capable of running modern mobile interfaces [Phosh](/wiki/Phosh "Phosh"), [Plasma Mobile](/wiki/Plasma_Mobile "Plasma Mobile") and [Sxmo](/wiki/Sxmo "Sxmo").

Other interfaces and devices are either for testing or serve a special purpose. For example, because of its hardware keyboard, one can use the classic [N900](/wiki/Nokia_N900_(nokia-n900) "Nokia N900 (nokia-n900)") with [i3wm](/wiki/I3wm "I3wm").

## <span id="Principles" class="mw-headline">Principles</span>

Decisions related to development of Nura are done with the following principles in mind.

### <span id="Developer_facing" class="mw-headline">Developer facing</span>

#### <span id="Easy_to_modify" class="mw-headline">Easy to modify</span>

Nura should be easy to modify and it should be easy to contribute the changes back.

<span class="small">Examples:</span>

<span class="small"></span>

- All packages in one [pmaports.git](/wiki/Pmaports.git "Pmaports.git") repository
- Simple packaging format <a href="https://wiki.alpinelinux.org/wiki/APKBUILD_Reference" class="external text" rel="nofollow">APKBUILD</a>
- [pmbootstrap](/wiki/Pmbootstrap "Pmbootstrap") makes it easy to:
  - Create a custom installation
  - Cross compile packages
  - Build packages from local source tree
  - Create foreign arch chroots
  - Reset the chroots to start over
- It's easy to enable SSH
- Lots of CI scripts assist in contributing changes back

<span class="small"></span>

<span class="small"></span>

#### <span id="Sustainable_and_maintainable" class="mw-headline">Sustainable and maintainable</span>

Nura should have maintainable code and packages. When patching software to fix builds or to fit our needs, we attempt to upstream everything that makes sense. [Device specific](/wiki/Device_specific_package "Device specific package") code and configuration should be minimal.

Devices in the [main category](/wiki/Device_categorization "Device categorization") must use a [(close to) mainline](/wiki/(Close_to)_Mainline "(Close to) Mainline") kernel.

<span class="small">Related:</span>

<span class="small"></span>

- <a href="/wiki/Create_a_package#Guidelines_for_packaging_patches" class="mw-redirect" title="Create a package">Guidelines for packaging patches</a>

<span class="small"></span>

<span class="small"></span>

#### <span id="Minimal_base" class="mw-headline">Minimal base</span>

It must be possible to install a minimal version of Nura.

<span class="small">Use case example:</span>

<span class="small"></span>

- Mainlining a new device with a minimal rootfs

<span class="small"></span>

<span class="small"></span>

#### <span id="Infrastructure" class="mw-headline">Infrastructure</span>

The infrastructure of Nura should consist of free and open source software.

### <span id="User_facing" class="mw-headline">User facing</span>

#### <span id="Polished" class="mw-headline">Polished</span>

Apps should make sense together and not give conflicting instructions. Broken features shall be disabled.

<span class="small">Examples:</span>

<span class="small"></span>

- <a href="https://gitlab.postmarketos.org/postmarketOS/pmaports/-/merge_requests/1449#note_385456592%7C" class="external text" rel="nofollow">pmaports!1449</a>: first run screen of GNOME software disabled
- <a href="https://gitlab.nura.eco/nura/pmaports/-/merge_requests/1443" class="external text" rel="nofollow">pmaports!1443</a>: broken "logout" button in Phosh hidden

<span class="small"></span>

<span class="small"></span>

#### <span id="Avoid_distractions" class="mw-headline">Avoid distractions</span>

User interfaces and apps should aid users in their workflows, and not distract them.

<span class="small"><a href="https://medium.com/thrive-global/how-technology-hijacks-peoples-minds-from-a-magician-and-google-s-design-ethicist-56d62ef5edf3" class="external text" rel="nofollow">"How Technology is Hijacking Your Mind"</a> is an excellent article on this topic, illustrating how this is a problem with current mainstream smartphone OS and apps. Examples for distractions:</span>

<span class="small"></span>

- Advertising
- Notifications for unimportant events
- "Recommendations" to try out specific features
- Autoplay of next videos

<span class="small"></span>

<span class="small"></span>

#### <span id="Prefer_free_software_services" class="mw-headline">Prefer free software services</span>

Integrations with services that run on proprietary software, or provide proprietary software, should not be enabled by default or recommended. But it should still be easy to enable them if the user desires (by having them behind an "additional providers" button or similar). If we have no means to test if integration with a proprietary service is working or not, we shall disable it.

<span class="small">Examples for proprietary services:</span>

<span class="small"></span>

- Flatpak + Flathub
- YouTube

<span class="small"></span>

Related issues:

<span class="small"></span>

- <a href="https://gitlab.nura.eco/nura/pmaports/-/work_items/725" class="external text" rel="nofollow">pmaports#725</a>: gnome-online-accounts: hide / disable proprietary services

<span class="small"></span>

<span class="small"></span>

#### <span id="Reliable" class="mw-headline">Reliable</span>

Updates should not break Nura on the <a href="https://nura.eco/blog/2020/05/31/three-years/#stable-release-channel" class="external text" rel="nofollow">stable channel</a>. Long term, it would be great to allow users to recover from failed updates.

<span class="small">Related issues:</span>

<span class="small"></span>

- <a href="https://gitlab.nura.eco/nura/pmaports/-/work_items/492" class="external text" rel="nofollow">pmaports#492</a>: make it possible to roll back upgrades

<span class="small"></span>

<span class="small"></span>

#### <span id="Privacy_friendly" class="mw-headline">Privacy friendly</span>

##### <span id="Encryption" class="mw-headline">Encryption</span>

The user's data should be protected with encryption unless they explicitly choose to use an unencrypted communication channel. Full disk encryption has been implemented since day one in Nura.

Long term, we should push towards integrating and preferring end-to-end encrypted communication.

<span class="small">Related issues:</span>

<span class="small"></span>

- <a href="https://gitlab.nura.eco/nura/pmaports/-/work_items/726" class="external text" rel="nofollow">pmaports#726</a>: Integrate EteSync into Phosh / Plasma Mobile on Nura

<span class="small"></span>

<span class="small"></span>

##### <span id="Security" class="mw-headline">Security</span>

Nura should use state-of-the-art security to protect the user's data from malicious input, such as websites or PDF documents.

<span class="small">Related issues:</span>

<span class="small"></span>

- <a href="https://gitlab.nura.eco/nura/pmaports/-/work_items/1596" class="external text" rel="nofollow">pmaports#1596</a>: privilege separation

<span class="small"></span>

<span class="small"></span>

##### <span id="Avoid_tracking" class="mw-headline">Avoid tracking</span>

Long term, it should be hard to fingerprint the user and collect data about them when they use Nura. (Currently we have merely changed the user-agents to something more generic.)

<span class="small">Related issues:</span>

<span class="small"></span>

- <a href="https://gitlab.nura.eco/nura/pmaports/-/work_items/727" class="external text" rel="nofollow">pmaports#727</a>: Phosh: bluetooth is always re-enabled after boot

<span class="small"></span>

<span class="small"></span>

#### <span id="No_vendor_lock-in" class="mw-headline">No vendor lock-in</span>

In Nura, we aim to build generic software solutions (programs, apps, ...), which can be adapted by other distributions if they choose to do so. Branding should be optional and sane patches to make our software work better on other systems should be accepted.

This benefits the user, as it is easier for them to switch between distributions. Also it makes development easier, because instead of each project developing their own solution for certain problems, we can work together.

<span class="small">Examples:</span>

<span class="small"></span>

- osk-sdl
- mobile-config-firefox
- on-device installer (distro-agnostic components now live upstream, Nura specific branding is in a separate repository called postmarketos-ondev)
- megapixels

<span class="small"></span>
